## Re-audit: cancel_subscription() refund handling

**Verdict:** The original finding is resolved, but the fix introduced a new high-severity regression: retried cancellations can now issue duplicate Stripe refunds.

| Severity | Status | Evidence | Impact | Recommendation |
|---|---|---|---|---|
| High | **Resolved** | `billing/subscriptions.py:1-8` — `stripe_client.refund(sub.charge_id)` now executes after the `with db.transaction():` block has exited (line 5 commits, line 7 calls Stripe). The `SELECT ... FOR UPDATE` lock is released before the network call. | DB lock is no longer held for the duration of an external Stripe call. | None — original issue addressed as recommended. |
| High | **New (regression introduced by this fix)** | `billing/subscriptions.py:4-7` commits `status = "canceled"` *before* calling `stripe_client.refund`, with no idempotency key and no refund-status field recorded on `sub`. `billing/worker.py:1-6` catches *any* exception from `cancel_subscription` and requeues the message unconditionally — the file's own comment confirms this "will call `cancel_subscription` again, including `stripe_client.refund`." | Moving the refund outside the transaction decoupled "mark canceled" from "issue refund," but nothing was added to make that decoupling safe under retry. If `stripe_client.refund` throws for any reason *after* Stripe has actually processed the refund (timeout, connection reset before the response is read, transient 5xx after processing, etc.), `handle_cancel_message` requeues and calls `cancel_subscription(sub_id)` again. The subscription is already `"canceled"`, so the second pass re-fetches it, re-commits the (unchanged) status, and re-issues `stripe_client.refund(sub.charge_id)` — with no idempotency key and no check for a prior refund. Stripe has no way to deduplicate the call, so the customer can be refunded twice for the same charge. This is a financial-correctness bug, not a cosmetic one, and it exists precisely because the transactional coupling that the original fix removed was never replaced with an idempotency mechanism. | Give the refund call a stable idempotency key derived from `sub.charge_id` (or `sub_id`) so Stripe collapses retried calls into one effect — this is the cheapest fix and requires no schema change. Additionally, add a `refund_status` field (`pending` / `refunded`) set inside the original transaction and checked at the top of `cancel_subscription` before calling Stripe, so a requeued message short-circuits once a refund has already been initiated. Do not rely on `worker.py`'s blanket `except Exception: requeue` to stay safe — it retries on every failure mode, including ones where the side effect already landed. |

**Why this counts as the fix's fault, not a pre-existing gap:** before the fix, the refund call and the status commit were inside the same locked transaction, so a crash between them was far less reachable in practice (the lock serialized concurrent attempts, though it didn't fully solve atomicity either). Pulling the refund out to fix the lock-holding problem is the right structural move, but it changes `cancel_subscription` from "one guarded operation" into "two independent side effects with no reconciliation," and `worker.py`'s retry policy was never updated to reflect that. The two files together — not either one in isolation — produce the double-refund path, which is exactly the kind of second-order failure a re-audit should catch.

**Smallest reversible next step:** add the Stripe idempotency key first (single-line change in `subscriptions.py`, no schema migration, immediately closes the duplicate-refund path even under the current blind-retry worker). Verify with a test that calls `cancel_subscription` twice for the same `sub_id`/`charge_id` and asserts Stripe's mock records only one effective refund. Track the `refund_status` column as a follow-up if reconciliation/observability into partial failures is also wanted.
