# Ports-and-adapters vs. layered structure — `billing_service`

## Recommendation

Neither side of the debate matches what's actually in the repository, so adopt neither wholesale. `billing_service/service.py` has no layered structure to preserve today — it's a single 8-line method that does routing, persistence, and payment-gateway I/O inline. A full hexagonal restructuring (multiple ports, domain/application/infrastructure layers, event plumbing) is disproportionate to an 8-line service with one caller and one adapter each. The useful part of the hexagonal argument here is narrower: introduce two seams — `InvoiceRepository` and `PaymentGateway` — around the two concrete, volatile dependencies the method currently calls directly, and keep `BillingService.charge` as a thin orchestrator over them. That is the smallest change that gets you the property people actually want out of "ports-and-adapters" (substitutable, testable boundaries), without inventing layers the code doesn't have a second consumer for yet.

## Evidence

- `service.py:1-7` is the entire scope under review — no controller, domain, or repository layer exists elsewhere in this directory (confirmed by listing: `service.py` is the only file). So "keep the current layered structure" is not a real option — there is no layering to keep. This is a conflict between how the request frames the choice and what the code shows; flagging it rather than silently picking a side.
- `conn = db.connect()` (`service.py:3`) and `stripe_client.charge(...)` (`service.py:5`) are direct calls to concrete, global infrastructure objects, invoked from inside the same method that holds the business rule ("charge this invoice"). There is no interface between the rule and either dependency, and no way to exercise `charge()` without a live DB connection and a live Stripe client.
- `service.py:5-6` charges Stripe, then updates the invoice row, with no transaction boundary and no idempotency key passed to `stripe_client.charge`. If the `UPDATE` fails or the process dies between lines 5 and 6, the invoice is charged in Stripe but still shows as unpaid — a retry will double-charge the customer. This is a correctness defect independent of which structural style is chosen; hexagonal vs. layered does not fix it by itself.

Lenses applied: **information hiding / ownership** (as primary — the method currently owns no boundary around either dependency, so callers/tests can't act on the rule without acting on the infrastructure) challenged by **evolutionary architecture** (is the migration cost of a boundary justified by the system's actual life span and consumer count right now?). At this scale the challenge wins on scope (no full hexagonal ceremony) but not on the core move (a boundary is still justified — see next section).

Note: this decision would normally also draw on `references/architectural-philosophies.md` for the deeper academic grounding a live team disagreement like this usually warrants (Parnas on information hiding, Cockburn on ports-and-adapters, Fowler on evolutionary design). That file is not present anywhere in this environment. The recommendation below is grounded directly in the lens definitions and the inspected code rather than that reference; this does not change the recommendation's confidence, since the case rests on concrete coupling and a concrete correctness bug, not on abstract doctrine.

## Tradeoffs

- **Full hexagonal restructuring** (ports for repository, payment, notifications; separate domain/application/adapter layers; domain events) — not justified by evidence. There is one call site, one DB adapter, one payment adapter, and no second implementation of anything on the horizon. The ceremony cost (interfaces, wiring, mapping types across layers) would exceed the value for a method this size, and nothing here needs runtime substitutability beyond tests.
- **Status quo (leave `service.py` as-is)** — fails on two counts already visible in the code: `charge()` cannot be unit-tested without a real database and a real Stripe account, and the dual-write bug above stands uncorrected. Coupling business logic directly to the Stripe SDK also means any Stripe client upgrade or vendor swap touches the business rule itself.
- **Recommended minimal seam** (`InvoiceRepository` + `PaymentGateway` interfaces, with the current `db`/`stripe_client` calls becoming the sole adapter implementations) — gets a test seam and isolates the two volatile dependencies (DB driver, third-party SDK) behind stable, service-owned contracts. Sacrifices: one interface + one adapter file per dependency, slightly more indirection than a single inline method. Does not by itself fix the dual-write bug — that needs an explicit decision (idempotency key on the Stripe call, plus either a transactional update or a reconciliation/outbox step), independent of the structural style.

## Next step

Smallest reversible action: extract `PaymentGateway` (method: `charge(amount, customer_id) -> ChargeResult`) and `InvoiceRepository` (methods: `get(id)`, `mark_charged(id)`) as interfaces; move the existing `stripe_client.charge` call and the two `db`/SQL calls into `StripePaymentGateway` and `SqlInvoiceRepository` adapters; `BillingService.charge` takes both as constructor dependencies and calls only the interface methods. No other call sites change.

Validate with a unit test for `BillingService.charge` using fake adapters, covering: happy path, and payment-succeeds-but-repository-update-fails (this should currently reproduce the double-charge risk — use it to decide the idempotency fix). Reversal condition: if no second adapter or test consumer materializes for either interface within a few iterations, collapse back to direct calls — the boundary isn't earning its cost.

**OPEN DESIGN DECISION**: how to close the dual-write gap — idempotency key + retry-safe re-check before charging, vs. transactional outbox — is unresolved and needs a call on acceptable latency/complexity from whoever owns billing correctness. Resolve by checking whether `invoice.status` is already `charged` (or a Stripe idempotency key already exists) before issuing a new charge, and by writing a regression test that reproduces the crash-between-charge-and-update scenario.
