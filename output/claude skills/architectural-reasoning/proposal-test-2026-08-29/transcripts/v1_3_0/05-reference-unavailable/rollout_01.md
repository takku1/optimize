**Recommendation**

Don't frame this as "layered vs. hexagonal" for the code as it currently stands — the file in scope has no layering to preserve and no hexagon to build around. `BillingService.charge` (billing_service/service.py:1-7) is a single method that opens a DB connection, reads a row, calls Stripe, and writes a status update, all inline, in one place. The right move is to introduce two narrow seams — not a full hexagonal rewrite — driven by what actually varies: a `PaymentGateway` port around the Stripe call, and an `InvoiceRepository` port around the two SQL statements. That captures the real value hexagonal architecture is sold on (substitutability for tests, isolation of a volatile third-party dependency) without imposing a domain/application/adapter split on a service that, as evidenced, is currently a single class with a single method.

Before any restructuring, the more urgent problem in this file is a fault-containment gap, not a layering gap: the Stripe charge and the invoice status update are two independent side effects with no transaction or idempotency guard between them. If the process dies, or `conn.execute` on line 6 fails after line 5 succeeds, the customer has been charged but the invoice is never marked `charged` — nothing here stops a retry from charging the same invoice twice. That risk exists regardless of which structural pattern wins the debate; neither "keep it layered" nor "go hexagonal" fixes it by itself. It needs an explicit fix (idempotency key on the Stripe call, ordering the write before/after confirmation, and a way to detect and reconcile the partial-failure state), independent of this decision.

**Tradeoffs**

- *Full hexagonal restructuring now*: gains a stable, uniform port/adapter boundary and a clean seam for testing and substitution. Costs real effort — interfaces, adapters, wiring, a domain/application split — applied to a service that isn't shown, in the evidence available, to have more than this one entry point. The cost likely exceeds the demonstrated need at this scope.
- *Two narrow ports (`PaymentGateway`, `InvoiceRepository`) without a full layer rewrite*: gains the concretely evidenced benefits — Stripe is a volatile external dependency and a natural test seam; the SQL access is worth hiding behind a repository so persistence details stop leaking into billing logic — at low structural cost. Sacrifices the uniformity a full hexagonal pass would give if the rest of the service (out of scope here) turns out to have the same problem in other methods.
- *Leave it exactly as-is*: no cost now, but leaves the untested, tightly-coupled Stripe/DB access in place and does nothing about the atomicity gap, which is the higher-severity, correctness-affecting risk (double-charging a customer) regardless of which side of the structural debate wins.

**Next step**

1. Introduce `PaymentGateway` (wrapping `stripe_client.charge`) and `InvoiceRepository` (wrapping the two SQL statements) as minimal interfaces; `BillingService.charge` becomes an orchestrator depending on both. This delivers the "port" half of hexagonal architecture where the evidence justifies it, without committing to restructuring the rest of the service.
2. Close the idempotency/atomicity gap directly: pass an idempotency key derived from `invoice.id` to the Stripe call, and treat "charged but not yet marked" as a recoverable state the repository or a reconciliation job can detect and retry safely, rather than an unhandled crash scenario.
3. **OPEN DESIGN DECISION**: whether the rest of the billing service (not in scope here) has enough additional volatility, external-dependency surface, or team-boundary pressure to justify extending this pattern into a full hexagonal restructuring. This should be resolved by inspecting the other files/entry points in `billing_service/` and asking the team what specifically motivated the hexagonal proposal — a concrete pain point (e.g., untestable Stripe calls elsewhere, an anticipated second payment provider) would tip this toward the broader restructuring; if the motivation is primarily stylistic, the narrow two-port fix above already resolves what the current evidence supports, at a fraction of the cost.
