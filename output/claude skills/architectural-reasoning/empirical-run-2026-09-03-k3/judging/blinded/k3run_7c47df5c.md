# Recommendation

Stop routing this through Platform's PR-review-and-deploy pipeline for every change. Instead, have Platform expose a **stable, versioned template contract** — the data/fields a notification can carry, the allowed customization points, and the safety rules (escaping, sandboxing, size/rate limits) — and let each consuming team own and deploy its own template content against that contract, independently of Platform's release cycle. Platform's involvement shifts from per-change manual review to occasional contract evolution plus automated conformance checks (schema validation, golden-render tests, a sandboxed template language) that run in CI without a human in the loop.

# Evidence

From what's described: two teams need small, recurring rendering changes; each one currently requires a Platform-authored PR review and a Platform-owned deploy; Platform itself names the review queue as the bottleneck; the constraint is explicitly "without growing the team." No repository was provided, so this is reasoned from the stated topology, not from inspected code — treat the contract shape below as a target to validate against the actual template engine before committing to it.

# Reasoning

**Governing force — sociotechnical alignment.** The team boundary (feature teams who know their own copy, fields, and edge cases) doesn't match the current change boundary (all rendering logic lives inside the Platform-owned service, so every edit must cross a team boundary to ship). That mismatch converts *change frequency* into *cross-team communication overhead*: every small, low-risk tweak queues behind Platform's review capacity regardless of how well-understood the change actually is. This is Conway's Law biting back — the code doesn't reflect who actually has the knowledge to change it safely, so the org pays a coordination tax on every commit.

**Challenge — end-to-end responsibility.** Is Platform actually the right authority for the *correctness* of feature-specific rendering content? Probably not — they don't own the domain semantics of what each feature's notification should say, so their review is likely more rubber-stamp than substantive, adding latency without adding much correctness. The content itself belongs with the team that understands it; what Platform should keep owning end-to-end is the *safety* of the rendering path — injection/escaping, template-language sandboxing, backward compatibility, blast radius if a template misbehaves. Splitting it this way — content ownership to the requesting teams, contract-and-safety ownership to Platform — routes each responsibility to the team that can actually discharge it, and removes Platform from a queue it was never well-positioned to clear quickly.

This does not require runtime fragmentation — no new service, no split deploy topology is implied by the problem as stated. It requires an explicit extension point inside the existing service: templates as versioned, schema-validated data owned by the consuming team, with Platform's own deploy only triggered when the rendering engine or the contract itself changes, not when a template's content changes.

# Tradeoffs

Platform gives up direct veto over every content change — it loses fine-grained control and some consistency guarantees it currently gets "for free" from manual review. In exchange, consuming teams gain the autonomy they're asking for, but also take on responsibility for their own template quality and bugs; that only works if automated guardrails (schema validation, sandboxed rendering, golden-output tests) are strong enough to replace what manual review was actually catching — otherwise this just trades a review bottleneck for a reliability problem. Building that contract and its validation tooling is real, upfront work for Platform, but it's a one-time (or occasionally-revisited) cost against a currently recurring, linearly-scaling one.

# Next step

Platform should audit what's actually varying across these change requests — which parts of the template are genuinely per-feature (copy, conditional fields, layout choices) versus what must stay fixed (delivery semantics, compliance footers, injection-unsafe constructs) — and turn that boundary into an explicit versioned schema with automated conformance checks the requesting teams can run in their own CI. Migrate the two teams' templates onto that contract so their changes ship on their own cadence. **OPEN DESIGN DECISION:** whether templates get a fully decoupled deploy path (hot-reloadable config, separate pipeline) or still ride Platform's deploy but skip manual gating — resolve this against how tightly the notification service's release process is already coupled to its deploy artifact, which isn't knowable without inspecting the actual service.
