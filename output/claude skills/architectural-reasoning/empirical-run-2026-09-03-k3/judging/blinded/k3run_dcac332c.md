Re-audit: cancel_subscription() fix (2026-08-01 finding)

**Findings**

| Severity | Status | Evidence | Impact | Recommendation |
|---|---|---|---|---|
| High (original) | **Resolved** | `billing/subscriptions.py:1-8` — `stripe_client.refund(sub.charge_id)` now executes after the `with db.transaction():` block exits, so the `SELECT ... FOR UPDATE` lock on the subscriptions row is released (via `db.commit()`, line 5) before the Stripe call runs. | The original problem — a slow/hung Stripe call holding a DB row lock open — no longer occurs; lock scope is now confined to the local status update. | None; the recommendation from the prior audit was implemented as stated. |
| High (new) | **New** | `billing/subscriptions.py:7` — `stripe_client.refund()` is called with no idempotency key, no pre-check, and no persisted "refund attempted/succeeded" state. `billing/worker.py:1-6` — `handle_cancel_message` retries on *any* exception raised out of `cancel_subscription` by requeueing the message, and the comment on line 6 confirms this replays the refund call. | Moving the refund outside the transaction decoupled it from the status commit: by the time `refund()` can fail, `sub.status = "canceled"` is already durably committed. Any exception from the Stripe call (timeout, dropped connection after Stripe already processed the refund, transient 5xx, etc.) now triggers `requeue(msg)`, which re-invokes `cancel_subscription`: the status update is a no-op (already canceled), but `stripe_client.refund(sub.charge_id)` fires again — unconditionally, with no dedup. This is a duplicate-refund path with real financial impact, and it's silent: nothing in this code path detects or prevents it. | Give the refund call an idempotency key (Stripe supports this natively — derive it deterministically from `sub.charge_id` or `sub_id` so repeated calls collapse into one refund on Stripe's side). Additionally, persist refund state on the subscription row (e.g. `refunded_at`) and check it before calling Stripe, so a re-entrant `cancel_subscription` from a requeue can't re-attempt a refund that already committed. The worker's blanket catch-and-requeue is also too coarse for a two-phase operation like this (DB commit + external side effect); a failure after the DB commit should route to a narrower, dedup-safe refund-retry path rather than re-running the whole handler. |

**Assessment**

The diff fixes exactly what it was written to fix — the lock-during-network-call problem — but the fix relocated the failure mode rather than removing it. The prior version's risk was a stuck lock; this version's risk is a duplicate charge-side-effect, because the operation was split into a DB step and an external step with no coordination between them, and the queue's retry semantics assume the whole handler is safely re-runnable. It isn't, once the DB half has committed. This should stay open as a new High-severity finding rather than being folded into the original ticket as closed-and-done.
