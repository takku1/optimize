## Re-audit: `cancel_subscription()` refund-during-lock fix

**Verdict: the original issue is resolved, but the fix introduces a new — and more severe — correctness bug, made worse by an unrelated file in the same code path.**

| Status | Severity | Evidence | Impact | Recommendation |
|---|---|---|---|---|
| **Resolved** | (was High) | `billing/subscriptions.py:2-7` — the `with db.transaction()` block now closes at line 5 (query, status write, commit); `stripe_client.refund()` moved to line 7, after the block exits. The `SELECT ... FOR UPDATE` row lock is released at commit, before the Stripe call. | None — confirms the fix matches the recommendation: the DB lock no longer spans the external network call. | None needed. |
| **New — High** | High | `billing/subscriptions.py:5,7` — `db.commit()` durably sets `status = "canceled"` *before* `stripe_client.refund(sub.charge_id)` runs, with no `try/except` around the refund call and no compensating write if it fails. | The transaction boundary that used to make "canceled" and "refunded" atomic is gone. If `stripe_client.refund` raises (timeout, 5xx, network error), the subscription is left permanently `canceled` with **no refund issued and no record that one is owed**. Either (a) write a `refund_status="pending"` row atomically with the cancellation and process the actual Stripe call from that durable intent (outbox/saga pattern), so a crash after commit still has a record to reconcile from, or (b) at minimum wrap the refund call and, on failure, write a compensating `refund_status="failed"` marker in a new short transaction so the divergence is queryable and alertable rather than silent. |
| **New — High (compounding)** | High | `billing/worker.py:2-6` — the queue consumer retries `cancel_subscription` on *any* exception, unconditionally requeuing (`# retries the handler on any exception, no dedup/idempotency key`). Combined with the finding above: a retry re-enters `cancel_subscription`, finds `status` already `"canceled"` (idempotent no-op), and unconditionally re-issues `stripe_client.refund(sub.charge_id)` at line 7 again — with no idempotency key passed to Stripe and no check for an existing refund. | Any failure mode where the first refund actually succeeded at Stripe but the handler didn't return cleanly (client-side timeout on the response, exception in surrounding code, etc.) now produces a **second real refund** on retry. This is the standard at-least-once-delivery-meets-non-idempotent-API bug, and it exists specifically because the fix decoupled refund from the transaction that used to gate retries on rollback. | Pass a stable idempotency key to `stripe_client.refund` (e.g. derived from `charge_id` or `sub_id`) so retries are safe at the Stripe layer regardless of what `worker.py` does. This is the higher-leverage fix — it also covers retry paths not visible in this file (timeouts, redeploys, manual replays). |

### Why this happened
The prior fix treated "move the call outside the transaction" as the whole fix. It correctly removed the lock-hold problem (an **information hiding / resource-scope** fix) but didn't address that the transaction boundary was also doing double duty as an **atomicity/fault-containment boundary** between "subscription state" and "refund happened." Splitting them without adding any replacement durability mechanism (idempotency key, outbox record, or reconciliation state) traded a lock-contention risk for a money-correctness risk — and `worker.py`'s blanket retry policy, unchanged and not touched by this diff, is what turns that gap into an active duplicate-refund bug rather than a latent one.

### Verification path
No test suite or repro was available in this input set to execute against; the above is a static-evidence read of `subscriptions.py` and `worker.py`. To confirm before shipping a fix: a test that (1) makes `stripe_client.refund` raise after the DB commit and asserts the subscription is *not* left in a silent `canceled`-without-refund state, and (2) simulates a requeue after a successful-but-acknowledgment-lost refund and asserts Stripe sees only one refund call (via a captured idempotency key) would falsify or confirm both new findings directly.
