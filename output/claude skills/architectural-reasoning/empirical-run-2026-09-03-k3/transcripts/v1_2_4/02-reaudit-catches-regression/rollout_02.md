## Re-audit: cancel_subscription() refund handling

**Scope:** billing/subscriptions.py, billing/worker.py

| Severity | Status | Evidence | Impact | Recommendation |
|---|---|---|---|---|
| High (2026-08-01) | **Resolved** | subscriptions.py:1-8 — `stripe_client.refund(sub.charge_id)` (line 7) now sits after the `with db.transaction():` block (lines 2-5) exits and commits, per the inline comment confirming the intent. | The `SELECT ... FOR UPDATE` lock is released at commit before the Stripe call runs, so a slow/hung Stripe request no longer holds the row lock open for the duration of the network call. The originally reported blocking risk is gone. | None needed for this specific issue. |
| High (new — introduced by this fix) | **Regression** | subscriptions.py:4-7 combined with worker.py:1-6. The status write (`sub.status = "canceled"`) is now committed *unconditionally and before* the refund call, so success/failure of `stripe_client.refund` is no longer coupled to the transaction at all. worker.py retries on any exception with no dedup or idempotency key: `except Exception: requeue(msg)  # will call cancel_subscription again, including stripe_client.refund`. `stripe_client.refund(sub.charge_id)` is called with no idempotency key visible in this call. | Splitting the refund out of the transaction removed the one thing that made the old code safe-by-accident: previously, moving the call kept it inside the retry's blast radius but at least the row lock forced serialization. Now, correctness depends entirely on the refund being safe to repeat, and it isn't. Concretely: if `stripe_client.refund` succeeds on Stripe's side but the call raises before returning cleanly to the worker (timeout, connection reset, transient 5xx after processing) — exactly the class of failure that motivated moving it out of the lock in the first place — `handle_cancel_message` catches the exception and requeues. The retry re-enters `cancel_subscription`, re-commits `status = "canceled"` (already true, so this masks the retry), and calls `stripe_client.refund(sub.charge_id)` again with no idempotency key to make Stripe dedup it — a second real refund to the customer. Separately, because status now commits independently of refund outcome, a subscription can be left permanently marked "canceled" with no refund ever issued if the retry path stops firing (e.g., message dropped, max-retry ceiling, poison-message handling elsewhere) — there's no durable refund-attempted/refund-succeeded state to reconcile against. | Make the refund idempotent at the Stripe boundary — pass an idempotency key derived from `sub_id`/`charge_id` (Stripe's `Idempotency-Key` request option) so a repeated call is a no-op on Stripe's side regardless of retry behavior. In addition, track refund outcome as its own durable field (e.g. `refunded_at`) separate from `status`, and have `cancel_subscription` check it before calling Stripe again — so "cancel" and "refund" are each idempotent and independently retriable rather than one silently masking the other on retry. |

**Verification path:** confirm by (1) checking whatever `stripe_client.refund` wraps for an idempotency-key parameter — not present in the two files in scope, so treat as absent until shown otherwise; (2) a repro: call `cancel_subscription`, force `stripe_client.refund` to raise after its Stripe-side effect lands, let `handle_cancel_message` requeue, and confirm a second refund call fires with the same `charge_id` and no dedup key.

**Bottom line:** the original finding (lock held across a network call) is fixed as recommended. The fix, applied without adjusting for the surrounding retry semantics in worker.py, introduces a new High-severity issue: duplicate-refund risk and status/reality drift on retry, because moving the call outside the transaction also moved it outside of anything that made "cancel" and "refund" happen together exactly once.
